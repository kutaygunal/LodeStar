TestForge — IT&V Plan, Execution & Reporting Gap Analysis

An honest, commercial-grade assessment of the TestForge module against leading test-management and verification tools (VectorCAST, Rapita RapiTest, LDRA, Jama, Polarion, Codebeamer, TestRail, NI TestStand, Keysight).

Module: TestForge Scope: IT&V lifecycle Benchmark: 9 commercial tools Type: Gap analysis (no code changes)

Executive Summary

Maturity: 2.5 / 5 — "Functional prototype, not yet a verification product"

Verdict. TestForge is a clean, well-factored engine that proves the core IT&V loop — plan → execute → report → persist — and it already wires into TraceLink (executed coverage) and AssureCheck (compliance evidence). That is a genuinely useful foundation. However, as a product it is a single-threaded, single-user, offline prototype. It has no test-case design intelligence, no parallel or real-time execution, no code coverage, no certification-ready evidence, no workflow/lifecycle, no dedicated UI, and no CI/CD or external-tool execution path. A verification lead or DO-178C auditor would not accept it today for anything beyond internal smoke testing.

Top 5 gaps (see prioritized list for the full set):

  • G1 — No test-case design intelligence. PlanGenerator only copies a supplied check list into steps; it cannot derive equivalence classes, boundary values, or MC/DC cases from a requirement or source. This is the single biggest authoring gap vs. VectorCAST/LDRA/Rapita.
  • G2 — No real execution path. TestRunner consumes a single IMeasurementProvider; the Spirent/R&S/Skydel adapters exist but are not wired into execution. No HIL, no parallel runs, no deterministic timing, no data acquisition.
  • G3 — No code coverage. Coverage is requirement-level only (via TraceLink). Statement/decision/MC/DC structural coverage — the core of DO-178C verification — is absent.
  • G4 — No certification-ready reporting. Output is Markdown + JSON only. No DO-178C evidence package, no result-to-requirement traceability in the report, no PDF/Word/ReQIF export.
  • G5 — No workflow or governance. No test-case lifecycle, review/approval, baselines, change-impact, RBAC, or audit trail. No dedicated TestForge UI.

Strategic recommendation. Do not try to out-build VectorCAST or TestStand on execution and coverage. Position TestForge as the orchestration and evidence layer: keep the plan/execute/report loop, add test-case design heuristics, wire the existing RF adapters into execution, delegate structural coverage to an external engine (or add a lightweight statement/decision pass), and invest in workflow + certification reporting. That is the differentiated, achievable path.

Deep-Dive per Area

1 Test Authoring

Have

  • PlanGenerator builds a TestProcedure from a scenario id + a list of checks.
  • Each check becomes an ordered, UUID'd TestStep with metric, expected value, tolerance.
  • Convenience checksFromObjective for ad-hoc smoke checks.
  • Version string on procedures; objective text captured.

Commercial

  • VectorCAST / LDRA / Rapita auto-generate test cases from source code and requirements.
  • Equivalence partitioning, boundary-value analysis, decision tables, MC/DC case generation.
  • Reusable test libraries, templates, and parameterized / data-driven tests (TestRail, Jama, TestStand).
  • Test-case editors with preconditions, steps, expected results, attachments.

Gap

  • No test-case design intelligence — PlanGenerator is a thin "checks → steps" copier.
  • No equivalence / boundary / MC/DC derivation from a requirement or source.
  • No reusable libraries, templates, or parameterized tests.
  • No test-case editor; authoring is code-level only.

Assessment. The automation claim ("~90% authoring reduction") is not yet credible: the generator does not design tests, it merely formats a caller-supplied list. This is the highest-leverage authoring gap.

2 Test Execution

Have

  • TestRunner executes steps sequentially against an IMeasurementProvider.
  • Clean Passed / Failed / Blocked semantics; run-level terminal status.
  • MockMeasurementProvider for offline / smoke runs.
  • Run start/finish timestamps captured.

Commercial

  • Parallel execution across targets/cores (VectorCAST, TestStand).
  • Hardware-in-the-loop and real-time execution (TestStand, Keysight, NI).
  • Deterministic timing, scheduling, and data acquisition (NI, Keysight).
  • Live instrument control and result streaming.

Gap

  • Single-threaded, sequential only — no parallel or scheduled runs.
  • No HIL, no real-time, no deterministic timing, no data acquisition.
  • RF adapters (Spirent/R&S/Skydel) are not wired into TestRunner.
  • No live streaming; results are computed after the fact.

Assessment. Execution is a proof-of-concept. The adapters exist but the execution engine never calls them, so the platform cannot actually drive a GNSS simulator today.

3 Measurement & Analysis

Have

  • Per-step metric capture with expected value and tolerance.
  • Pass/fail decision: |actual − expected| ≤ tolerance.
  • Blocked handling when a metric is unavailable.
  • Deviation reported in the failure message.

Commercial

  • Multi-sample statistics, mean/σ, min/max, histograms (Keysight, NI).
  • Trend / regression analysis across runs (Rapita timing, TestRail).
  • Anomaly detection and uncertainty quantification.
  • Complex pass criteria (multiple thresholds, logical conditions).

Gap

  • Single scalar comparison only — no statistical analysis.
  • No trend, regression, or anomaly detection.
  • No uncertainty / confidence quantification.
  • No multi-sample or time-series measurement model.

Assessment. Adequate for a single pass/fail check; insufficient for the statistical rigor a GNSS verification program expects (e.g. CEP/95, repeatability).

4 Coverage

Have

  • Requirement coverage via TraceLink: designed / executed / verified.
  • Executed coverage reflects real TestForge run results (test_run_coverage, migration 017).
  • Latest-run-governs semantics for verified status.
  • Wired into AssureCheck evidence.

Commercial

  • Structural code coverage: statement, decision, branch, MC/DC (VectorCAST, LDRA, Rapita).
  • Requirement-to-test traceability with coverage % (Jama, Polarion, Codebeamer).
  • Coverage gap highlighting and analysis.

Gap

  • No code coverage at all — statement/decision/MC/DC absent.
  • Coverage is requirement-level only; no structural metrics.
  • No coverage gap analysis or drill-down.

Assessment. The requirement-coverage integration is a genuine strength and differentiator. But DO-178C verification hinges on structural coverage, which is entirely missing.

5 Reporting

Have

  • Markdown report (header, counts, per-step table).
  • Structured JSON report.
  • TestReport summary with conclusion.
  • Persisted runs enable historical reporting.

Commercial

  • Certification-ready DO-178C evidence packages (LDRA, Rapita, VectorCAST).
  • Result-to-requirement traceability in the report (Jama, Polarion).
  • PDF / Word / HTML / ReQIF / CSV export.
  • Sign-off and approval workflow on reports.

Gap

  • No certification-ready evidence package.
  • No result→requirement traceability embedded in the report.
  • No PDF/Word/ReQIF export (Markdown + JSON only).
  • No sign-off / approval on reports.

Assessment. Reporting is developer-friendly but not auditor-friendly. The AssureCheck module produces richer HTML/CSV/JSON compliance reports; TestForge should reuse that pattern and add traceability + export.

6 Workflow

Have

  • Procedure version string.
  • Run status lifecycle (Pending → Running → Passed/Failed/Blocked).
  • Transactional persistence of procedures and runs.

Commercial

  • Test-case lifecycle: draft → review → approved → obsolete (Jama, Polarion, Codebeamer).
  • Review / approval with sign-off and audit trail.
  • Baselines and change-impact analysis on tests.
  • Multi-user concurrency control.

Gap

  • No test-case lifecycle states.
  • No review / approval workflow.
  • No baselines or change-impact on tests.
  • No multi-user / concurrency control.

Assessment. Governance is essentially absent. A verification program cannot demonstrate controlled change without lifecycle, review, and baselines.

7 Integration

Have

  • ScenarioForge: procedures reference a scenario id.
  • TraceLink: executed coverage wiring (test_run_coverage).
  • AssureCheck: evidence pulls TestForge run results.
  • RF adapters (Spirent/R&S/Skydel) exist in the adapters layer.

Commercial

  • Native RF tool remote control (Spirent, R&S, Skydel).
  • CI/CD integration (VectorCAST, TestStand, Jenkins plugins).
  • ALM / requirements integration (Jama, Polarion, Codebeamer).
  • Test data management and external test-case import.

Gap

  • RF adapters not wired into TestRunner execution.
  • No CI/CD integration or CLI for headless runs.
  • No REST API for TestForge (AssureCheck has one; TestForge does not).
  • No external test-case import / test data management.

Assessment. Internal integration (TraceLink, AssureCheck) is good. External integration (RF tools, CI/CD, API) is the missing half — and the adapters are already 80% there.

8 UX

Have

  • No dedicated TestForge UI.
  • TraceLink UI views exist (Graph, Matrix, Coverage Dashboard, Impact, Baseline Diff).

Commercial

  • Test plan editor (TestStand sequence editor, TestRail).
  • Run dashboard with live status (TestRail, Jama).
  • Results browser with gap highlighting (VectorCAST, LDRA).

Gap

  • No test plan editor.
  • No run dashboard.
  • No results browser or coverage gap highlighting.

Assessment. TestForge is invisible in the UI. The TraceLink views prove the team can build good Qt views; TestForge needs the same treatment.

9 Commercial Readiness

Have

  • Clean, testable C++17 core with unit + smoke tests.
  • Transactional SQLite persistence.
  • Integrates with TraceLink and AssureCheck.

Commercial

  • Audit trail and RBAC (all enterprise tools).
  • Certification evidence and sign-off.
  • Multi-user, concurrency, enterprise DB.
  • Support, docs, training, licensing.

Gap

  • No audit trail or RBAC in TestForge.
  • No certification evidence or sign-off.
  • No multi-user / concurrency control.
  • No REST API, CLI, or CI/CD entry point.

Assessment. A verification lead or auditor would find the module technically sound but operationally incomplete: no governance, no evidence, no external entry point.

Prioritized Gap List

Priorities: P0 blocks the core value proposition · P1 required for commercial credibility · P2 differentiators / polish. Effort is a relative engineering estimate.

  • P0G1 — Test-case design intelligenceEffort: M (2–3 sprints)
    PlanGenerator must derive test cases from a requirement/objective — equivalence partitioning, boundary-value analysis, and (for software) MC/DC case generation. Why: without it the "auto-authoring" claim is hollow and the module cannot compete with VectorCAST/LDRA/Rapita.
  • P0G2 — Wire RF adapters into executionEffort: M (2 sprints)
    Connect Spirent/R&S/Skydel adapters to IMeasurementProvider so TestRunner can drive a real GNSS simulator and read live measurements. Why: the platform's core promise is automating real IT&V; today it only runs against a mock.
  • P0G3 — Structural code coverage (statement/decision/MC/DC)Effort: L (3–4 sprints)
    Add a lightweight statement/decision coverage pass, or integrate an external coverage engine, and surface MC/DC metrics. Why: DO-178C verification is defined by structural coverage; requirement-level coverage alone is insufficient.
  • P0G4 — Certification-ready reporting + traceabilityEffort: M (2 sprints)
    Produce DO-178C-style evidence packages with result→requirement traceability, and add PDF/Word/ReQIF export (reuse AssureCheck's ReportService pattern). Why: auditors need traceable, exportable evidence, not Markdown.
  • P0G5 — Workflow: lifecycle, review, baselines, RBAC, auditEffort: L (3–4 sprints)
    Add test-case lifecycle states, review/approval, baselines, change-impact, RBAC, and an audit trail. Why: no governance means no controlled change, which is a hard blocker for certification and multi-user use.
  • P1G6 — Dedicated TestForge UIEffort: L (3–4 sprints)
    Test plan editor, run dashboard, and results browser with coverage-gap highlighting, matching the quality of the existing TraceLink Qt views. Why: the module is currently invisible to users.
  • P1G7 — Parallel & scheduled executionEffort: M (2 sprints)
    Support parallel test runs and scheduled/headless execution. Why: real verification programs run many tests; sequential single-thread is a throughput blocker.
  • P1G8 — REST API + CLI for TestForgeEffort: M (2 sprints)
    Expose plan/run/report via REST (mirroring AssureCheck's API server) and a headless CLI. Why: enables CI/CD and external-tool integration.
  • P1G9 — Statistical analysis & anomaly detectionEffort: M (2 sprints)
    Add multi-sample statistics (mean/σ, min/max, histograms), trend/regression across runs, and basic anomaly detection. Why: GNSS verification needs statistical rigor (CEP/95, repeatability).
  • P2G10 — Reusable test libraries & parameterized testsEffort: M (2 sprints)
    Support reusable test libraries, templates, and data-driven/parameterized tests. Why: reduces authoring effort and matches TestRail/Jama expectations.
  • P2G11 — CI/CD integrationEffort: S (1 sprint)
    Jenkins plugin / pipeline step to trigger TestForge runs and publish results. Why: continuous verification in the dev loop.
  • P2G12 — External test-case import & test data managementEffort: M (2 sprints)
    Import test cases from CSV/ReQIF and manage test data sets. Why: interoperability with existing test assets.

Recommended Roadmap

Phase 1 · Foundation
Make the core loop real.
  • Wire RF adapters into TestRunner (G2) — real execution against Spirent/R&S/Skydel.
  • Add test-case design heuristics: equivalence + boundary derivation (G1, first slice).
  • Add REST API + CLI (G8) for headless/CI entry.
Phase 2 · Credibility
Become auditor-acceptable.
  • Certification-ready reporting with result→requirement traceability + PDF/Word/ReQIF (G4).
  • Workflow: lifecycle, review/approval, baselines, RBAC, audit (G5).
  • Structural code coverage — statement/decision first, MC/DC next (G3).
Phase 3 · Scale & UX
Make it usable and fast.
  • Dedicated TestForge UI: plan editor, run dashboard, results browser (G6).
  • Parallel & scheduled execution (G7).
  • Statistical analysis & anomaly detection (G9).
Phase 4 · Differentiate
Own the integration layer.
  • Reusable libraries & parameterized tests (G10).
  • CI/CD integration (G11).
  • External test-case import & test data management (G12).
  • Full MC/DC + coverage gap analysis (G3 complete).
Positioning note. TestForge should not try to out-build VectorCAST (structural coverage) or TestStand (execution) head-on. Its durable advantage is the integrated IT&V loop — plan, execute, and report with requirement coverage and compliance evidence in one place. The roadmap above prioritizes making that loop real (execution + design), then trustworthy (evidence + governance), then scalable (UI + parallel), then differentiated (libraries + CI).
