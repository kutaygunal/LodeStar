Product Manager Challenge · Gap Analysis

ScenarioForge vs. Commercial GNSS/SBAS Simulation Tools

An honest, commercial-grade assessment of the software-defined GNSS/SBAS scenario generator against Spirent GSS9000 + SimGEN, Rohde & Schwarz SMW200A + GNSS suites, Skydel, Keysight, and u-blox.
Module: ScenarioForge (Lodestar / VeriNav) Basis: Verified C++ source (core/scenario, ~3,500 LOC) Date: 2026-08-12 Author: pm-scenarioforge

1. Executive Summary

Verdict: ScenarioForge is a credible, self-contained mathematical / data-level GNSS simulation engine — a strong foundation for software-in-the-loop (SIL) PVT, NMEA, RINEX, and SBAS integrity work. It is not yet a commercial GNSS/SBAS signal simulator.

The single largest gap is that ScenarioForge produces numbers, not signals. Commercial tools (Spirent, R&S, Skydel) generate real RF/IF waveforms with controlled power, CN0, multipath, and interference that a receiver under test actually tracks. ScenarioForge computes satellite geometry, pseudoranges, PVT, and NMEA text — it cannot drive a physical receiver or a hardware-in-the-loop (HIL) bench.

Within its chosen lane (software-defined, data-level simulation), ScenarioForge is genuinely differentiated: it has real SGP4/SDP4 orbit propagation, Klobuchar ionosphere, Saastamoinen troposphere, SBAS fast/long-term corrections, and HPL/VPL integrity — math that most "scenario generators" skip. The path to commercial relevance is to own the software-defined niche (Skydel-style) rather than chase RF hardware.

Have Frames, Keplerian, SGP4/SDP4, RINEX, NMEA, PVT, error models, SBAS integrity Partial Multi-constellation, scenario modeling, interoperability Missing RF/IF signal generation, trajectory builder, multipath, interference, GBAS, GUI, HIL

Top 5 gaps (by commercial impact)

  1. No RF/IF signal generation — cannot drive a receiver under test; the core value of a GNSS simulator.
  2. No trajectory / vehicle-motion builder — receiver is a static ECEF point + velocity; no dynamic flight/vehicle scenarios.
  3. No multipath, interference/jamming, or antenna-pattern modeling — the RF impairments test engineers care most about.
  4. No multi-GNSS / multi-frequency native support — only GPS broadcast ephemeris + TLE; no Galileo/GLONASS/BeiDou, no L1/L2/L5.
  5. No GUI, no scripting/automation API, no vendor export — a C++ library only; no scenario editor, visualization, or HIL interface.

3. Deep-Dive per Area

3.1 Signal Generation

Have: None. ScenarioForge computes satellite geometry, pseudoranges, PVT, and NMEA text. It produces no RF/IF waveform, no baseband samples, no carrier/PRN code, no power/CN0.
Commercial: Spirent GSS9000 + SimGEN, R&S SMW200A + GNSS suites, Skydel, and Keysight generate real RF/IF signals for GPS/Galileo/GLONASS/BeiDou across L1/L2/L5 with per-satellite power, CN0, AGC, and fading. This is the core deliverable of a GNSS simulator — it is what a receiver under test actually tracks.
Gap: The defining gap. ScenarioForge is a data-level simulator, not a signal simulator. It cannot drive a physical receiver or a HIL bench. This is the single most important thing separating it from commercial tools.

3.2 Scenario Modeling

Have: A static receiver ECEF position + velocity vector, an elevation mask, and per-epoch step(). Error models (clock/iono/tropo) can be toggled.
Commercial: Full trajectory builders (waypoints, flight/vehicle/rover profiles, 6-DOF motion), multipath ray-tracing, urban-canyon reflection, interference/jamming (CW, wideband, chirp, spoofing), antenna patterns, and dynamic time-varying scenarios.
Gap: No trajectory engine, no multipath, no interference, no antenna patterns, no dynamic scenario scripting. Test engineers spend most of their time building these scenarios; ScenarioForge has no way to express them.

3.3 Constellation Fidelity

Have: Keplerian propagation from GPS broadcast ephemeris, TLE parsing, and a full SGP4/SDP4 propagator (Vallado 2006, deep-space terms). Constellation aggregation with visibility + elevation mask. This is real, defensible orbit math.
Commercial: High-precision numerical propagation (J2/J3, full gravity field), SP3 precise ephemeris, almanac, satellite health/availability flags, and native multi-GNSS broadcast ephemeris (Galileo F/NAV, GLONASS, BeiDou).
Gap: SGP4 is LEO/TLE-grade, not broadcast-grade for MEO GNSS. No high-precision propagator, no SP3, no almanac, no health/availability, and no native Galileo/GLONASS/BeiDou ephemeris (only GPS + generic TLE).

3.4 SBAS / GBAS

Have: SBAS message parsing (CRC-verified), fast + long-term corrections, ionospheric grid (IGP) interpolation, and integrity computation producing HPL/VPL protection levels from UDRE/GIVE. This is a genuine strength — most scenario tools omit integrity math.
Commercial: Full SBAS message generation for WAAS/EGNOS/GAGAN, ionospheric grid generation, augmentation accuracy, and GBAS/LAAS ground-station augmentation.
Gap: ScenarioForge parses and applies SBAS corrections and computes integrity, but does not generate SBAS messages or model a GBAS ground station. Integrity (HPL/VPL) is a differentiator to build on.

3.5 Receiver Modeling

Have: A weighted least-squares PVT solver with DOP (PDOP/HDOP/VDOP), pseudorange and Doppler computation, and clock/iono/tropo error models feeding the measurements.
Commercial: Receiver dynamics, tracking-loop models, multipath and interference robustness, measurement noise, and carrier-phase processing (RTK-capable).
Gap: No tracking loops, no measurement noise model beyond deterministic error models, no carrier-phase/RTK, no receiver dynamics. The PVT solver is solid but the receiver is idealized.

3.6 Interoperability

Have: RINEX NAV + OBS parsing (v3.00) and NMEA GGA/RMC/GSA/GSV/ZDA output with verified checksums. Clean C++ API.
Commercial: RINEX import/export, SP3 precise products, vendor scenario interchange (Spirent/R&S/Skydel formats), vendor binary protocols, and hardware-in-the-loop interfaces.
Gap: No RINEX write, no SP3, no vendor export, no HIL. NMEA + RINEX parsing is a good base but the ecosystem connectors are missing.

3.7 Performance

Have: Single-threaded C++ step() per epoch. Deterministic math, no external deps (self-contained Vec3/Mat3).
Commercial: Real-time stepping, hundreds of simultaneous channels, high update rates, and certified determinism for HIL.
Gap: No real-time loop, no channel-count concept, no timing guarantee, no parallel execution. Fine for offline SIL; not ready for real-time HIL.

3.8 UX

Have: None — a C++ library/API only. No scenario editor, no visualization, no trajectory builder, no results analysis.
Commercial: Scenario editors, 3D sky/ground visualization, trajectory builders, and results-analysis dashboards are standard.
Gap: No UI at all. Even a minimal Qt scenario editor + 2D/3D visualization would dramatically improve usability and demo-ability.

3.9 Commercial Readiness

Have: Real, verified GNSS math; a clean, dependency-free C++ API; a self-verifying smoke path. A credible engineering foundation.
Commercial: RF hardware, certification, GUI, scripting/automation (Python/SCPI), multi-user, licensing, documentation, and support.
Gap: A GNSS test engineer would expect: a way to drive a receiver (RF or at least baseband), a scenario editor, a scripting API, and vendor export. All are missing. The realistic commercial path is software-defined baseband + Skydel-style automation, not RF hardware.

5. Recommended Roadmap

Phase A — Software-Defined Baseband (P0, the strategic bet)

Position ScenarioForge as a Skydel-style software-defined GNSS simulator rather than chasing RF hardware. Add I/Q baseband generation: PRN code generation, carrier, code phase, and per-satellite CN0/power control. This lets a software receiver (or a low-cost SDR front-end) track the signal — the core commercial value, without the cost of RF hardware.

Effort: L · Unlocks: receiver-under-test drive, HIL, the entire commercial story.

Phase B — Scenario & Impairment Engine (P0)

Add a trajectory/waypoint engine (6-DOF, flight/rover/vehicle profiles) and the two RF impairments that matter most: multipath and interference/jamming. Add multi-GNSS native ephemeris (Galileo/GLONASS/BeiDou) + almanac + health/availability.

Effort: M · Unlocks: realistic dynamic scenarios, the scenarios test engineers actually build.

Phase C — Automation & Interoperability (P0/P1)

Expose a Python + REST/SCPI-style automation API for CI and remote control. Add RINEX write, SP3, and vendor scenario export (Spirent/R&S/Skydel interchange) so ScenarioForge plugs into the existing commercial ecosystem rather than replacing it.

Effort: M · Unlocks: CI integration, ecosystem interoperability, automation-driven test.

Phase D — UX & Fidelity (P1/P2)

Build a Qt scenario editor with 2D/3D visualization and a trajectory builder. Add multi-frequency (L1/L2/L5), a high-precision orbit propagator + SP3, SBAS message generation + GBAS, and a real-time stepping loop with a channel model.

Effort: M–L · Unlocks: usability, demo-ability, high-accuracy and real-time use.

Strategic recommendation

Do not try to out-build Spirent/R&S on RF hardware — that is a capital-intensive, entrenched market. Instead, own the software-defined, automation-first niche (Skydel's playbook): a low-cost, scriptable, CI-friendly GNSS/SBAS simulator with real integrity math. ScenarioForge's existing SGP4, Klobuchar/Saastamoinen, SBAS corrections, and HPL/VPL integrity are a genuine head start that most competitors lack. The fastest path to commercial relevance is Phase A (baseband) + Phase C (automation).
