1. Executive Summary & Verdict

6.2/10

Verdict: AssureCheck is a solid, well-engineered compliance data & reporting engine — but it is not yet a certification-grade compliance tool. It has a clean standards registry, a working PASS/FAIL/NA/WARNING engine, evidence collection from TraceLink/TestForge, HTML/CSV/JSON reports, a REST API, and a dashboard. What it lacks is the semantic depth, workflow, and auditability that a certification authority or a paying customer expects.

The single most important finding is a correctness gap in the compliance engine: objectives are marked PASS when any entity of a heuristically-mapped type exists in the database — not when the objective is actually satisfied. This is the difference between a "checklist tracker" and a "compliance tool."

Top gaps (headline)

  • P0 Shallow evidence evaluation — the engine infers objective status from "does a row exist in a mapped table," not from whether the objective is genuinely met. A compliance authority would reject this as evidence.
  • P0 No verification-method / coverage analysis — no MC/DC, statement, or decision coverage computation, no analysis/test/inspection/demonstration distinction, no coupling analysis. This is the core value of LDRA/Rapita/VectorCAST.
  • P0 No certification evidence package — reports are flat tables; there is no auditor-ready evidence package with objective→evidence traceability, sign-off, or approval.
  • P1 No review/approval/waiver workflow — no objective status lifecycle, no sign-off, no deviations/waivers, no audit trail of who approved what.
  • P1 No multi-user / RBAC / audit — single-user, no roles, no permissions, no per-actor audit trail.
  • P1 Incomplete standard coverage — DO-178C Tables A-1..A-7 are fully represented (82 objectives), but DO-254, ARP4754A, ARP4761, and DO-278A are simplified subsets; tool qualification (DO-178C §12) is absent.
  • P2 No web UI / objective browser / gap highlighting — REST API + Qt dashboard data exist, but no interactive browser experience.
  • P2 No external evidence import (ReqIF/OSLC) — only internal TraceLink/TestForge evidence.
Bottom line: The engine and data layer are at roughly 60–70% of commercial parity. The verification-analysis, workflow, and certification-evidence layers — where LDRA, Rapita, VectorCAST, Visure, and Polarion differentiate — are largely missing. AssureCheck is a credible foundation and a strong orchestration/integration layer, but it must add semantic evaluation, coverage analysis, and an approval/audit workflow before it can be sold as a certification tool.

3. Deep-Dive per Area (1–9)

3.1 Compliance Coverage

Have: Five standards seeded with 136 checklist items. DO-178C is represented by all seven tables (A-1..A-7) totalling 82 objectives — this matches the real standard's table structure. Each item carries an id, objective text, DAL range, and evidence hint.

Commercial: Vendors ship the full standard text, every objective, and the associated guidance/means-of-compliance. DO-178C also includes tool qualification (§12), and DO-254 has ~70 objectives across its tables (not 16). ARP4754A and ARP4761 have far more objectives than the 16 and 11 listed here.

Gap: DO-178C is well covered, but the other four standards are simplified subsets. Tool qualification (DO-178C §12.2 / Table 11-1) is absent entirely. There is no linkage to the actual standard text or to the "means of compliance" guidance that auditors expect.

Risk: A customer certifying hardware (DO-254) or a system (ARP4754A/ARP4761) would find the objective set incomplete and would not trust the coverage % as a certification claim.

3.2 Certification Evidence

Have: Evidence links are attached to PASS results (entity type + id), collected from TraceLink (requirements/design/test/trace) and TestForge (test runs). Reports export as HTML/CSV/JSON with objective-coverage percentages.

Commercial: Tools produce an auditor-ready evidence package: each objective is traceable to concrete evidence artifacts, with sign-off, approval, and a formal package export (e.g., a DO-178C compliance matrix). Evidence is versioned and immutable.

Gap: AssureCheck produces flat tables, not a certification evidence package. There is no sign-off/approval workflow, no evidence versioning, and no formal objective→evidence traceability document. The evidence links are only populated on PASS and are not independently verifiable.

Critical: The evidence is heuristic — a PASS means "some row of the mapped type exists," not "this objective is demonstrably satisfied." This would not survive a certification audit.

3.3 Verification Methods

Have: The engine distinguishes only four evidence sources (test_cases, trace_links, design_items, requirements) via substring matching on the evidence hint. It does not model verification methods at all.

Commercial: LDRA, Rapita RapiTest, VectorCAST, and QA Systems support the four DO-178C verification methods (analysis, test, inspection, demonstration) and compute real structural coverage — statement, decision, and MC/DC — plus data/control coupling analysis. This is the core of their value proposition.

Gap: AssureCheck has no verification-method taxonomy and no coverage computation. It cannot tell you whether MC/DC was achieved for a DAL-A objective — it only checks whether any test case exists with a "Passed" status. Coupling analysis is absent.

Critical: For DO-178C objectives A6-8 (statement), A6-9 (decision), A6-10 (MC/DC), and A6-11 (coupling), AssureCheck cannot actually verify compliance. This is the single biggest functional gap vs. the verification-tool competitors.

3.4 DAL Handling

Have: DAL A–E is supported. Each checklist item carries a DAL range (A, A-B, A-C, A-D), and the engine marks items NA when the project DAL falls outside the range. The API accepts a dal parameter.

Commercial: Tools provide a DAL assignment workflow (assign DAL per item/component), show DAL-change impact, and generate per-DAL reports. DAL is a first-class, managed attribute.

Gap: DAL is a query parameter, not a managed attribute. There is no DAL assignment workflow, no DAL-change impact analysis, and no per-DAL report packaging beyond passing a string. The DAL applicability logic itself is correct (range check), but it is not surfaced as a workflow.

3.5 Workflow & Review

Have: A status enum (PASS/FAIL/NA/WARNING) per objective, persisted in assurance_checks. Results are idempotently replaced per standard.

Commercial: A full objective status lifecycle (e.g., Draft → In Review → Approved → Signed Off), review/approval with named approvers, waivers/deviations, and comments. Every status change is audited.

Gap: AssureCheck has no workflow. Status is computed, not managed. There is no review, no approval, no sign-off, no waiver/deviation, no comments, and no audit trail of who changed what. The checked_at column is hard-coded to the string "now" — there is no real timestamp or actor.

Note: The checked_at value is literally the string "now" in ComplianceEngine::storeResults. This is a placeholder, not a real timestamp — a concrete sign the workflow/audit layer is unfinished.

3.6 Reporting

Have: ReportService builds a per-standard/per-DAL report with coverage summary and exports to HTML, CSV, and JSON. Coverage % is computed as pass/applicable.

Commercial: Branded, versioned certification reports; per-standard and per-DAL packaging; audit trail of report generation; export to multiple formats including PDF and ReqIF; compliance matrices.

Gap: The HTML report is a minimal table (no styling, no cover page, no branding, no per-DAL packaging). There is no report versioning, no generation audit, no PDF, and no compliance-matrix export. CSV output does not escape commas/quotes in objective text (a correctness bug for real data).

Detail: toCsv concatenates fields with commas without quoting or escaping. Any objective text containing a comma or quote will corrupt the CSV — a real defect for a reporting feature.

3.7 Integration

Have: EvidenceService collects from TraceLink (entities + links) and TestForge (test runs) into an EvidenceSnapshot. A REST API (/assurecheck/*) exposes standards, checks, summary, and dashboard.

Commercial: Deep integration with requirements/test tools, import of external evidence (ReqIF, OSLC, test results from other tools), and a broad API surface.

Gap: Evidence is internal-only (TraceLink/TestForge). There is no ReqIF import of external evidence, no OSLC, and no way to attach evidence from third-party tools. The REST API is functional but narrow (5 routes).

Strength: The TraceLink module already has ReqIF import/export and a DO-178C evidence package. Wiring that into AssureCheck would close this gap cheaply.

3.8 UX

Have: DashboardService provides per-standard objective coverage data, and the Qt compliance dashboard consumes it. A REST API serves the data.

Commercial: Interactive browser-based dashboards with objective browsers, gap highlighting (red/green), filters, and drill-down. All leading tools are web-first and collaborative.

Gap: AssureCheck has data, not UI. There is no objective browser, no gap highlighting, no interactive matrix, and no web layer. The Qt app is not built. A stakeholder cannot visually review compliance today.

3.9 Commercial Readiness

Have: A clean, testable engine; REST API; performance hardening (batched/incremental, 10k-scale); idempotent result storage; a documented standards checklist.

Commercial: A certification authority or paying customer expects: auditable evidence, sign-off workflow, multi-user RBAC, tool qualification, real coverage analysis, and a web UI.

Gap: AssureCheck is not yet sellable as a certification tool. It is a strong foundation and integration layer. The missing pieces are exactly the ones that make a compliance tool trustworthy: semantic evaluation, coverage analysis, workflow/approval, audit, and multi-user support.

What to defend: The engine is clean, well-tested (6 suites green), performant, and REST-exposed. As an orchestration/integration layer that wraps LDRA/Rapita/VectorCAST via their APIs, it has genuine commercial value — matching the project's strategic positioning.

5. Recommended Roadmap

Phase A — Make it trustworthy (P0, ~4–6 weeks)

  • G1 Semantic evidence evaluation: define per-objective evaluation rules (not row-existence). This is the foundation — everything else builds on it.
  • G2 Verification-method taxonomy: tag each objective with its means of compliance (analysis/test/inspection/demonstration).
  • G5 Review/approval/sign-off workflow with real timestamps and actors (also fixes the "now" placeholder).
  • G4 Certification evidence package: objective→evidence traceability + exportable package (reuse TraceLink's existing DO-178C evidence package).

Phase B — Verification depth (P0/P1, ~4–6 weeks)

  • G3 Coverage analysis: integrate LDRA/Rapita/VectorCAST results via their APIs (strategic fit — do not re-implement MC/DC from scratch), or compute basic statement/decision coverage internally.
  • G10 Coupling analysis (integrate or implement).
  • G6 Complete the DO-254/ARP4754A/ARP4761/DO-278A objective sets + DO-178C tool qualification.

Phase C — Commercial parity (P1, ~4–6 weeks)

  • G7 Append-only audit trail.
  • G8 Multi-user / RBAC with named approvers.
  • G9 Waivers/deviations.
  • G11 Report hardening (CSV escaping, versioning, per-DAL packaging, branded HTML).

Phase D — UX & differentiation (P2, ~4–6 weeks)

  • G12 Web UI / objective browser / gap highlighting over the REST API.
  • G13 External evidence import (ReqIF/OSLC).
  • G14 DAL assignment workflow.
  • G15 OSLC integration.
Strategic recommendation: Position AssureCheck as the orchestration/integration layer that wraps LDRA/Rapita/VectorCAST for coverage and Visure/Polarion for requirements — rather than re-implementing MC/DC analysis from scratch. The engine's clean architecture, REST API, and performance make it an ideal compliance hub. Prioritize G1 (semantic evaluation) and G5 (workflow) first: without them, no certification claim is credible.
