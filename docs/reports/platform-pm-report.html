Lodestar is an ambitious, well-architected C++17 monorepo that has made genuine, verified engineering progress in three of its nine modules. TraceLink (requirements/design/interface/test traceability) is the most mature — a real graph engine with lifecycle state machines, audit trail, baselines, change-request workflow, impact/coverage/matrix analysis, a 9-rule compliance engine, FTS5 search, duplicate detection, ReqIF/CSV/HTML import-export, a full REST API with API-key auth, and hardening (WAL, indexes, 10k-scale performance). AssureCheck (ARP4754A/ARP4761/DO-178C/DO-254/DO-278A compliance) is a credible compliance engine with standards, checks, evidence, HTML/CSV/JSON reporting, coverage %, and a REST API. ScenarioForge contains real GNSS math — Keplerian/SGP4/TLE orbit propagation, ionosphere/troposphere/clock error models, PVT (pseudorange/Doppler/solver), RINEX, SBAS corrections/integrity, and NMEA generation.

However, as a product — something a customer could buy, deploy, and use to run a certification program — Lodestar is not yet shippable. The honest gaps are structural, not cosmetic:

Top gaps (the "why we can't sell it yet" list):
  1. Two flagship modules are stubs. RiskAI (LLM-assisted FMEA/hazard) and IntegrateHub (cross-disciplinary hub) are 5-line placeholders — yet they are two of the four "novel value" pillars in the pitch.
  2. No runnable application. The Qt views exist but the UI is not built (LODESTAR_BUILD_UI defaults OFF). There is no desktop app, and no web layer at all. Every commercial competitor is browser-based and collaborative.
  3. Adapters are connect/disconnect stubs. Spirent/R&S/Skydel/LLM/Python adapters only set connection state; there is no real vendor invoke logic, so no actual RF injection or LLM call works end-to-end.
  4. No multi-user, roles, or concurrent editing. Only API keys exist. No user accounts, permissions, review/approval workflows, or conflict handling — table stakes for every ALM competitor.
  5. No real-time / determinism validation. The GNSS math is real but there is no evidence of real-time performance, hardware-in-the-loop, or determinism guarantees — the core promise of the platform.
  6. Python intelligence layer and CI are skeletons. The Python layer is a README; the Jenkinsfile is checkout→build→self-verify only, with no test agents or matrix builds.
  7. No commercial packaging. No licensing, pricing, installers, support, or end-user documentation.

Bottom line: Lodestar has a differentiated, defensible engineering core (TraceLink + AssureCheck + ScenarioForge) that is ahead of where most greenfield tools get. But the market-facing surface — a runnable, collaborative, integrated product — is missing. The strategic recommendation from the README (position as the orchestration/integration layer wrapping vendor tools, with novel value in ScenarioForge and RiskAI) is sound, but it is not yet executed: the integration layer (adapters) and the novel-value modules (RiskAI, IntegrateHub) are exactly the parts that are stubbed.

3. Deep-dive per area (1–9)

3.1 End-to-end IT&V workflow

HaveScenarioForge generates scenarios (real math) → TestForge generates/executes plans → TraceLink traces requirements→test → AssureCheck checks compliance → ReportService exports HTML/CSV/JSON. Each stage exists as a library with passing tests.
CommercialSpirent PNT-Automation and R&S run the full loop in one connected environment: scenario → RF injection → measurement → analysis → report, with hardware in the loop and live dashboards.
GapThe stages are not wired together. There is no end-to-end path that takes a scenario, injects it into real hardware, collects measurements, and feeds them back into coverage/compliance. The seams are: (a) adapters don't actually invoke vendor tools, (b) TestForge runs are not linked into live coverage, (c) no orchestration layer drives the whole pipeline. The workflow is a set of libraries, not a product workflow.

3.2 Integration & interoperability

HaveREST API with API-key auth; ReqIF/CSV/HTML import-export; adapter pattern (Spirent/R&S/Skydel/LLM/Python/Mock) behind a common interface; JSON handling; HttpClient.
CommercialVendor tools expose mature automation APIs (Spirent PNT-Automation, R&S SCPI, Skydel API). ALM tools expose REST + OSLC and integrate with CI/CD, Jira, and test tools.
GapAdapters are connect/disconnect stubs — no real invoke() logic, so no vendor tool can actually be driven. No OSLC. No CI/CD integration (Jenkinsfile is skeleton). ReqIF is a genuine strength. The integration story is architectural but not functional.

3.3 Collaboration & multi-user

HaveAPI-key auth; change-request workflow (Open→InReview→Approved/Rejected→Implemented); review service; RBAC service exists in code (wp4_rbac_tests pass) but is not surfaced as user accounts.
CommercialEvery ALM tool (Jama, Polarion, Codebeamer, DOORS) has user accounts, roles, permissions, concurrent editing with conflict resolution, review/approval, comments, and notifications.
GapNo user model, no roles/permissions at the product level, no concurrent editing, no comments/notifications. The RBAC service is a code-level capability with no UI or user directory. This is a P0 for any collaborative ALM positioning.

3.4 Automation & AI

HaveDuplicate/similarity detection (threshold-based); rules engine (9 built-in compliance rules); auto-generated test plans; auto-reporting (HTML/CSV/JSON); LLM adapter exists (connect-only).
CommercialDOORS (Watson), Jama, Visure, ReqSuite, Innoslate ship AI quality scoring and suggestions. No competitor yet owns LLM-assisted FMEA — this is Lodestar's open lane.
GapRiskAI is a stub — the LLM-assisted FMEA/hazard differentiator is not built. The LLM adapter cannot actually call a model. No AI quality scoring on requirements. The automation that exists (rules, duplicate detection) is good but narrow.

3.5 Deployment

HaveCross-platform CMake (Windows MSVC, Linux GCC/Clang); SQLite persistence; config module; Qt Widgets desktop UI (views exist).
CommercialAll leading tools are browser-based SaaS or on-prem web apps with licensing, packaging, and multi-tenant scalability.
GapDesktop-only, and the desktop app is not even built (LODESTAR_BUILD_UI OFF). No web layer, no cloud, no licensing, no installers, no scalability story. SQLite is single-writer — fine for desktop, a blocker for multi-user web without a server DB.

3.6 Certification readiness

HaveAssureCheck compliance engine (ARP4754A/ARP4761/DO-178C/DO-254/DO-278A); append-only audit trail; baselines + diff + rollback; evidence package export; coverage %.
CommercialVectorCAST/LDRA/Rapita are certified toolchains with MC/DC analysis and DO-178C qualification evidence. DOORS/Codebeamer provide full audit + certification support.
GapLodestar has the data model and rules for compliance but no certified toolchain, no MC/DC analysis, and no qualification evidence. The audit trail and evidence package are strong foundations. Certification-readiness is a P1 — the rules engine is credible but unproven against a real certification audit.

3.7 UX & product polish

HaveQt view models + UI wiring service; views for matrix, graph, impact, coverage dashboard, baseline diff, document, project tree, detail panel. Tests pass (wp6_ui, wp7_view_models).
CommercialPolished browser dashboards with navigation, search, charts, onboarding, and role-based views.
GapThe views are code, not a product — the app is not built, so there is no runnable UI to evaluate. No onboarding, no charts beyond coverage, no role-based views. UX is the least-developed area and cannot be assessed as a product until the app builds.

3.8 Performance & reliability

HaveHardening: WAL, BEGIN IMMEDIATE, indexes, 10k-scale performance (5.5s), DB backup/restore, structured logging, input validation, typed error codes, FTS5 search.
CommercialSpirent/R&S guarantee real-time, deterministic RF output. ALM tools scale to thousands of concurrent users.
GapPersistence performance is genuinely good. But the core promise — real-time, deterministic GNSS — is unproven: no real-time benchmarks, no hardware-in-the-loop, no determinism tests. No concurrency story (single-writer SQLite). Reliability is good at the library level, unproven at the system level.

3.9 Commercial viability

HaveA clear, differentiated pitch (orchestration layer + ScenarioForge + RiskAI); a defensible engineering core; ReqIF strength; a real compliance engine.
CommercialCustomers expect: pricing, licensing, installers, support, documentation, training, reference customers, and a path to certification.
GapNothing commercial exists: no pricing, no packaging, no installers, no end-user docs, no support model, no sales collateral. The two differentiators that would justify a purchase (RiskAI, IntegrateHub) are stubs, and the integration layer that would wrap vendor tools is non-functional. You cannot sell a product whose headline features don't run.

5. Recommended roadmap

Three horizons, sequenced so that each delivers a demonstrable, sellable increment. The guiding principle: turn the strong engineering core into a runnable, integrated, collaborative product, then differentiate.

Horizon 1 — "Make it run" (P0, ~3–4 months)

  1. Build the desktop app. Turn the existing Qt views into a runnable application (enable LODESTAR_BUILD_UI, wire MainWindow to the service API). This immediately gives a demoable product.
  2. Make adapters functional. Implement real invoke() for at least one vendor (start with Skydel — software-defined, easiest to test) and the LLM adapter. Prove one end-to-end RF injection.
  3. Implement RiskAI. Ship LLM-assisted FMEA/hazard as the flagship differentiator — it is the most defensible novel value and no competitor owns it.
  4. Implement IntegrateHub. A cross-disciplinary issue/coordination hub to complete the "one platform" story.
  5. Add a user model + roles + permissions. Surface the existing RBAC service as real accounts with a login and role-based views.
  6. Validate real-time/determinism. Add real-time benchmarks and a hardware-in-the-loop smoke test to prove the core promise.

Horizon 2 — "Make it competitive" (P1, ~3–4 months)

  1. Web layer. Build a browser read/review layer over the REST API (the fastest path to collaboration without a full rewrite).
  2. Close the IT&V loop. Wire TestForge runs into live coverage and compliance so a test result updates the dashboard.
  3. Full CI/CD. Add automated test agents, a Windows/Linux matrix, and coverage reporting to the pipeline.
  4. Certification evidence path. Add MC/DC analysis and a DO-178C evidence workflow to make AssureCheck audit-ready.
  5. Commercial packaging. Licensing, installers, end-user docs, and a support model.

Horizon 3 — "Make it differentiated" (P2, ongoing)

  1. OSLC for interop with the DOORS/Polarion/Codebeamer ecosystems.
  2. AI quality scoring on requirements (builds on existing duplicate detection).
  3. Guided compliance templates/checklists for ARP4754A/DO-178C.
  4. Variants / branching for product-line engineering.
  5. Concurrent editing with conflict resolution once the web layer and user model are in place.
Strategic note. The README's positioning — orchestration/integration layer wrapping vendor tools, with novel value in ScenarioForge and RiskAI — is correct and defensible. The execution gap is that the integration layer (adapters) and the novel-value modules (RiskAI, IntegrateHub) are exactly the parts that are stubbed. Horizon 1 is essentially "execute the strategy that is already written down." If the team can ship a runnable product with a working RiskAI and one real vendor integration, Lodestar would occupy a lane no single commercial tool currently owns.
